# G6.3 — TLA+ core enforcement model

**Status:** model encoded; TLC execution pending  
**Model:** formal/tla/G6_RuntimeEnforcement.tla  
**Configuration:** formal/tla/G6_RuntimeEnforcement.cfg

## 1. Model scope

The first finite-state model isolates the synchronous acceptance protocol and its central races. It models two invocations, a fixed set of UCON-allowed invocations, one revocable capability, policy versions 1 and 2, JEPA advisory output, and the lifecycle through governance commit.

It encodes these interleavings:
- authorization before revocation;
- gate check before revocation;
- authorization under policy version 1 followed by publication of version 2;
- JEPA output changes before or after formal authorization;
- service acceptance followed by loss of the acceptance response;
- dispatch followed by a timeout before a confirmed acceptance;
- observation, verification, and commit.

The model deliberately makes the final Accept transition recheck the capability and policy version. This is the abstract linearization contract under test. It does not assume that an earlier GateCheck alone is sufficient.

## 2. State variables

| Variable | Meaning |
|---|---|
| status | Invocation lifecycle state |
| certPolicy | Policy version bound into the authorization certificate |
| gatePassed | Whether the invocation passed the explicit pre-dispatch gate |
| accepted | Whether the external service effect/acceptance actually occurred |
| acceptedWhileRevoked | Whether capability was revoked at the acceptance linearization point |
| acceptedWithFreshPolicy | Whether certificate policy matched the active policy at acceptance |
| observed | Whether a service observation/receipt has been obtained |
| verified | Whether the observed effect has been verified |
| committed | Whether governance commit occurred |
| outcomeUnknown | Whether the caller's outcome is ambiguous |
| capRevoked | Effective revocation state |
| policyVersion | Current authoritative policy version |
| acceptedPolicy | Policy version at external acceptance |
| jepa | Advisory predictor output; not read by authorization or acceptance guards |

## 3. Invariants configured for TLC

- TypeOK
- NoUnauthorizedAcceptance
- NoAcceptanceAfterRevocation
- NoStalePolicyAcceptance
- CommitRequiresVerification
- UnknownNotCommitted
- JepaCannotAuthorize

The no-authority property is intentionally represented as a safety invariant: any accepted invocation must belong to the UCON-allowed set. JEPA output is varied nondeterministically but is absent from the authorization and acceptance guards.

## 4. Ambiguous response semantics

The model distinguishes two cases:
1. Timeout after dispatch before a confirmed acceptance: the local outcome becomes UNKNOWN, with no acceptance asserted by this abstract transition.
2. Acceptance occurred, but the response was lost: the external acceptance remains true while the local status becomes UNKNOWN. Such an invocation cannot be committed without later reconciliation.

The model does not yet include a reconciliation action, retries, an idempotency-key table, or an asynchronous job that completes after acceptance. Those are explicit extensions for subsequent model iterations.

## 5. Deliberate abstraction limits

This core model does not yet encode:
- action, target, principal, delegation-chain, plan-hash, or certificate-signature fields;
- mutable resource balances or concurrent compare-and-apply;
- asynchronous job completion/cancellation;
- a full write-ahead log and crash-recovery protocol;
- multiple capabilities, resources, policy rules, or policy replicas;
- Byzantine components or real-time bounds.

Therefore, it cannot discharge all G4 assumptions. It is a first safety kernel, not the complete UCON-JEPA system model.

## 7. Required negative variants

Before treating this model as validated, create controlled mutant specifications:
- M1: remove the capability-revocation guard from Accept; expect NoAcceptanceAfterRevocation to fail.
- M2: remove the policy-version guard from Accept; expect NoStalePolicyAcceptance to fail.
- M3: allow Accept for any invocation irrespective of UCONAllowed; expect NoUnauthorizedAcceptance and JepaCannotAuthorize to fail.
- M4: allow Commit before Verify; expect CommitRequiresVerification to fail.

A model checker that reports no error on the positive model is not sufficient by itself. These negative controls test whether the invariants are capable of detecting the intended classes of defect.
