# G6.5 — Refinement map and executable runtime contract tests

**Status:** abstract reference contract tests pass; production refinement open

## 1. Purpose

G6.5 maps the G6.1 threat-model assumptions and G6.2 transition events to concrete implementation controls and executable tests. The tests in tests/G6/test_runtime_contract.py exercise a small reference protocol. They are not tests of a deployed MCP gateway, cloud connector, or enterprise service.

## 2. Refinement map

| Formal assumption / property | Required implementation control | Minimum verification evidence |
|---|---|---|
| Complete mediation (A-GATE) | Gateway-only routes and gateway-held credentials | Enumerate service/API operations; attempt direct calls with agent credentials; verify denial |
| Effective principal binding | Identity broker binds agent, delegated principal, and service credential | Confused-deputy tests; inspect credential subject/audience/scope |
| Certificate integrity (A-CERT) | Signed or integrity-protected certificate bound to invocation, action, target, principal, capabilities, policy and state versions | Mutation, replay, substitution, cross-principal and cross-target negative tests |
| Authoritative state (A-STATE) | Versioned policy/state authority; no stale cache at acceptance | Stale replica and cache invalidation tests |
| Evaluator semantics (A-SEM) | Versioned reference semantics and differential evaluator tests | Policy truth-table and differential test suite |
| Effect linearizability (A-ATOMIC) | Atomic service-side acceptance, CAS/transaction, reservation, or proved equivalent | Gate-vs-accept race tests for each adapter class |
| Revocation (A-REV) | Defined effective-revocation point serialized with acceptance | Revoke-before-accept must fail; accept-before-revoke may stand |
| Policy update (A-POL) | Policy epoch/version checked at acceptance | Update-before-accept must reject stale certificate |
| Mutation evidence (A-EVIDENCE) | Correlated receipt plus authoritative read-after-write or attestation | Forged, stale, missing, duplicated, and cross-invocation receipt tests |
| Commit authority (A-MUT) | Governance commit API accepts only verifier-produced evidence | Direct commit bypass and invalid evidence tests |
| Durable intent (A-LOG) | Write-ahead intent before dispatch; append-only durable event record | Crash injection at every protocol boundary |
| Serializable resource mutation (A-SERIAL) | CAS/ETag, serializable transaction, lock/reservation, or equivalent | Concurrent invariant tests and conflict schedule exploration |
| Predictor isolation (A-ISO) | JEPA has no credentials or API to issue authorization; output is advisory | Predictor failure, false-negative, arbitrary-output, and direct-bypass tests |
| Statistical scope (A-RISK) | Certificate binds score/model/policy/tool/label versions and sampling population | Version mismatch rejection, calibration-split integrity, cluster dependence checks |

## 3. Executable tests currently implemented

The reference contract suite contains ten tests:

1. successful request follows authorization → gate → acceptance → observation → verification → commit;
2. a positive JEPA recommendation cannot override UCON denial;
3. effective revocation after authorization but before acceptance blocks the effect;
4. policy publication after authorization but before acceptance blocks stale use;
5. the gate binds action, principal, and capability;
6. duplicate invocation identifiers are rejected;
7. commit before verification is rejected;
8. an uncorrelated receipt produces UNKNOWN and cannot be committed;
9. a lost acceptance response preserves the remote-effect fact while blocking premature commit;
10. all six permutations of revocation, policy update, and acceptance are checked against the expected ordering rule.

GitHub Actions run 44199165327 passed all ten tests (Python 3.12). These tests validate the reference harness, not production integration.

## 4. Gaps between the abstract harness and production

The reference runtime intentionally simplifies several concerns:
- it uses an in-memory set for revoked capabilities and a scalar policy version;
- it models UCON admission as a supplied Boolean rather than a full policy language;
- it does not implement cryptographic certificates or credential issuance;
- it does not model distributed replicas, network partitions, or real tool adapters;
- it does not implement a durable write-ahead log, crash recovery, or compensation;
- it does not model resource-level concurrent transactions or asynchronous jobs;
- its JEPA isolation is structural (the predictor output is not an authorization input), not a deployment permission audit.

No production guarantee follows until concrete adapters are mapped to the LTS and the relevant tests are run against the actual integration boundary.

## 5. Adapter conformance test plan

Every protected operation must have an adapter conformance record containing:
- service and API operation identifier;
- effect class T1–T6 from G6.1;
- effective principal and credential source;
- action canonicalization and certificate binding fields;
- gate location and concrete acceptance/linearization event;
- policy/state version protocol;
- revocation and policy-update race behaviour;
- idempotency key and retry contract;
- receipt correlation and verification method;
- asynchronous completion/cancellation behaviour;
- crash and reconciliation strategy;
- test IDs, execution environment, results, and evidence links.

A tool with no defensible acceptance point or insufficient effect evidence must be classified as weakly observable/ambiguous. The system must restrict its guarantee rather than inherit assumptions from another adapter.

## 6. Required next implementation work

Before claiming G4 implementation validation:
1. select one concrete reference adapter (recommended first: a synchronous conditional API with ETag/CAS support);
2. implement the gateway/adapter protocol against a sandbox service;
3. run the contract suite against the real adapter, not only the reference harness;
4. inject revocation, policy-update, timeout, duplicate, and crash races;
5. record service receipts and read-after-write evidence;
6. demonstrate no direct credential/network bypass;
7. produce a refinement argument mapping each concrete event to the abstract LTS.
