# G7.4 — Refinement histories and crash-boundary recovery

## Objective

G7.4 adds two forms of executable evidence beyond the G7.3 state-based tests:

1. a finite-history linearizability checker that enforces real-time precedence;
2. deterministic fault injection at the transaction's pre-commit and post-commit
   response boundaries.

The checker is implemented in `src/ucon_jepa/linearizability.py`. The
transactional service accepts an optional `fault_hook` used only by tests and
controlled experiments.

## Refinement relation

The concrete reference store state is mapped to the abstract state

[
alpha(S_c)=(v,p,e,G,X),
]

where:
- (v) is the selected resource's version;
- (p) is the policy version;
- (e) is the authorization epoch;
- (G) is the explicit grant relation;
- (X) is the revoked-principal set.

Concrete payload bytes, SQLite row identifiers, receipt digests, and event
sequence numbers are implementation metadata and are abstracted away, except
that the invocation record must preserve the command/result binding.

The abstract mutation transition accepts iff expected ((v,p,e)) match and
the principal is not revoked and has the required grant. It increments (v)
exactly once. The concrete implementation's accepted transaction performs the
same abstract state change, while its denied/conflicting transitions leave
(v) unchanged. A replay of the same invocation returns the stored result and
does not produce a second abstract mutation.

This is a forward-simulation argument for the stated SQLite implementation
under G7.3 assumptions A1–A5. It does not cover arbitrary external services,
SQLite storage corruption, unmodeled writers, or distributed database
implementations.

## History-based linearizability checker

A completed operation history records:
- invocation and response monotonic-clock timestamps;
- operation kind and bound arguments;
- observed result.

For every pair (a,b), if (a.response < b.invoke), the checker requires
(a) to precede (b) in every candidate sequentialization. It searches the
remaining topological orders and applies the abstract sequential specification.
A history is accepted iff at least one order both respects all real-time edges
and reproduces every observed result.

The algorithm is exhaustive over the supplied finite history. Its worst-case
search is exponential in the number of mutually overlapping operations; use
bounded batches and do not treat it as a high-throughput production monitor.

## Crash-boundary experiment

The test-only fault hook can raise at two exact boundaries:

- **before_commit:** all mutation writes have been issued but COMMIT has not
  occurred. The exception path rolls back; the resource and invocation record
  remain unchanged. Reusing the same invocation ID and identical command is
  therefore a new valid attempt.
- **after_commit:** COMMIT has completed but the response is deliberately
  suppressed by raising. A retry with the same invocation ID and command
  digest returns the original receipt; the resource version remains incremented
  exactly once.

The second case models a lost response after durable commit. It does not model
power-loss durability, torn storage, replica failover, or a real process kill
at every CPU instruction. Those require process-level and storage-level
fault-injection infrastructure.

## Evidence

The added tests include:
- six checker tests covering overlapping writes, mandatory real-time order,
  revocation and policy fencing, and malformed histories;
- pre-commit rollback;
- post-commit lost-response recovery.

Together with the previous 36 G7 tests, the expected G7 suite contains 44 test
methods. The CI run is the authoritative execution evidence.

## Assurance boundary

| Claim | Status |
|---|---|
| Finite histories accepted by checker have a sequential witness | PROVED by exhaustive checker search, conditional on its model/specification |
| Non-overlapping operations respect real-time precedence | TESTED with positive and adversarial negative histories |
| Pre-commit injected failure leaves no mutation | TESTED in SQLite reference store |
| Post-commit lost response replays the same receipt without duplicate mutation | TESTED in SQLite reference store |
| Actual power-loss and process-kill recovery | OPEN |
| Production PostgreSQL/distributed SQL refinement | OPEN |
| Exactly-once external side effects | NOT CLAIMED; generally requires idempotent receivers or deduplication |
| Liveness/fairness and tail latency under production contention | OPEN |

A database transaction and an external side effect cannot be made atomic merely
by writing an outbox row. A transactional outbox can atomically persist intent
with the database mutation, but dispatch is normally at-least-once; consumers
must deduplicate by a stable effect ID. G7.4 therefore does not claim
exactly-once delivery or atomicity across an arbitrary external tool/API.
