# G7.3 — Atomic authorization and resource mutation

## Objective

Replace the G7.1 conditional-header *proposal* with an executable server-side
reference semantics in which the following are validated in one transaction:

1. the expected resource version;
2. the current policy version;
3. the current authorization/revocation epoch;
4. the principal's current UCON grant and revocation status; and
5. the resource mutation and durable invocation receipt.

The reference implementation is `src/ucon_jepa/transactional_service.py`.
It uses one SQLite database and `BEGIN IMMEDIATE` for every protected state
transition. Revocation, policy changes, and resource mutations all acquire the
same SQLite writer lock and commit in that transaction domain.

## State and transition model

Let the committed database state be

`S = (R, P, E, G, X, I)`, where:

- `R[r] = (v, payload)` is a resource and its monotonically increasing version;
- `P` is the policy version;
- `E` is the authorization epoch;
- `G` is the set of explicit (principal, action, resource) grants;
- `X` is the set of revoked principals;
- `I` maps invocation identifiers to immutable command digests and results.

A mutation command is

`m = (i, s, a, r, v*, p*, e*, b)`.

It is accepted only if, in the same write transaction:

[
v^*=R[r].version land p^*=P land e^*=E
land s\notin X land (s,a,r)\in G.
]

On acceptance, the service atomically changes the resource version to
`v* + 1`, stores the new payload, appends an event, and stores a correlated
receipt under invocation ID `i`. On any failed precondition, it records a
non-accepting outcome and leaves the resource unchanged.

Identical retries with the same invocation ID and command digest return the
original result. Reuse of an invocation ID for a different command raises
`IdempotencyConflict`. Invocation IDs are durable within this database, not
globally distributed identifiers.

## Theorem G7.3-A — Atomic acceptance safety (reference-store theorem)

Assume:

- **A1 — Single transactional domain.** Resource rows, policy version, epoch,
  grants, revocations, invocation records, and event records reside in the same
  SQLite database.
- **A2 — Writer serialization.** The storage engine correctly implements
  SQLite `BEGIN IMMEDIATE` writer serialization and transaction atomicity.
- **A3 — Complete state-transition discipline.** Every policy/grant/revocation
  update and every protected resource mutation uses this service and the same
  database. No out-of-band writer modifies these tables.
- **A4 — Trusted input binding.** The caller identity, action, resource ID and
  payload have already been authenticated and bound by the upstream reference
  monitor. This module does not implement cryptographic identity verification.
- **A5 — Database integrity.** The database is not maliciously modified and
  committed transactions are durable under the configured SQLite/storage
  guarantees.

Then for every invocation `i` whose stored outcome is ACCEPTED, at its
transaction's serialization/commit point (t_i):

[
egin{aligned}
R_{t_i^-}[r].version &= v^*,\
P_{t_i^-} &= p^*,\
E_{t_i^-} &= e^*,\
s &\notin X_{t_i^-},\
(s,a,r)&\in G_{t_i^-},
end{aligned}
]

and the same atomic commit changes the resource version to (v^*+1) and
stores the invocation receipt. No transaction that commits a revocation or
policy/epoch change before (t_i) can be bypassed by this mutation.

### Proof sketch

By A1–A3, each relevant state transition obtains the SQLite writer lock via
`BEGIN IMMEDIATE`; concurrent writers cannot interleave their protected
read/check/write sections. A mutation reads (R,P,E,G,X) only after acquiring
that lock. The code returns ACCEPTED only in the branch where all five
preconditions hold. The resource update, event insertion, and invocation
record are executed before the same COMMIT. By A2 and A5, either all these
writes commit or none do. A concurrent revocation or policy update is ordered
before or after this transaction: if before, the mutation reads the changed
state and its expected epoch/version check fails (or the revoked/grant check
denies); if after, the mutation's acceptance linearizes first. Therefore the
claimed acceptance implication holds for this reference database. QED,
conditional on A1–A5.

This is a proof about the stated reference transition system and SQLite
transaction assumptions. It is **not** a proof that an arbitrary remote API,
distributed SQL deployment, cache, or external side effect has these
semantics.

## Linearizability and concurrency evidence

The service allocates monotonically increasing event sequence numbers while
holding the same serialized writer transaction. The race tests use these
sequences to check the real-time ordering of mutation and revocation commits.

The suite includes:
- stale resource-version, policy-version, and authorization-epoch rejection;
- explicit revocation and absent-grant denial;
- no partial resource update on rejected commands;
- invocation replay and conflicting idempotency-key reuse;
- 24 concurrent mutations against one expected resource version (exactly one
  may be accepted);
- 40 independent mutation-versus-revocation races. Each accepted mutation
  must have an event sequence before revocation; otherwise the mutation must
  be non-accepting and ordered after revocation;
- a concurrent policy-update race;
- an API-surface test demonstrating that a JEPA score is not an authorization
  parameter.

These are executable concurrency tests, not exhaustive model checking or a
formal proof of SQLite's implementation.

## Security and deployment limitations

| Property | G7.3 status |
|---|---|
| Atomic check of resource version, policy version, epoch, grant and revocation | PROVED under A1–A5 for this reference service |
| Concurrent writers cannot both commit the same expected resource version | TESTED; follows from theorem assumptions |
| Revocation/update versus mutation ordering | TESTED by bounded race campaign; follows from theorem assumptions |
| Durable idempotency in one database | TESTED |
| Multi-region/distributed database linearizability | OPEN |
| External side-effect atomicity (email, payment, cloud API, agent tool) | OPEN |
| Production identity verification and delegation binding | OPEN |
| Network-enforced complete mediation | OPEN |
| Secret broker and downstream credential enforcement | OPEN |
| Crash/failover durability under production storage configuration | OPEN |
| Liveness/fairness under contention | OPEN |

The service must not be deployed as a shared network-filesystem database or
treated as a distributed coordination layer. A production adapter must
demonstrate an equivalent transaction/conditional-command primitive in the
actual resource-owning service. If authorization state and the resource cannot
participate in one atomic transaction, use an explicit fencing/lease protocol
or co-locate the authorization epoch with the resource's authoritative
version; otherwise the joint guarantee remains OPEN.

## JEPA boundary

JEPA scores, embeddings, predictions, or confidence values do not appear in
the mutation authorization predicate. They may prioritize or recommend
candidate actions, but only the trusted identity binding and explicit current
UCON policy state authorize a mutation.
