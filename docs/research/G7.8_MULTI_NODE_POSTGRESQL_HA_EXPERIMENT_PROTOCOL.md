# G7.8 — Multi-node PostgreSQL HA and failover experiment protocol

## Status and scope

**Status: EXPERIMENT SPECIFICATION — NOT YET EXECUTED.**

G7.8 tests the deployment boundary that G7.7 deliberately leaves open: real primary/standby replication, externally controlled promotion, old-primary fencing, acknowledged-commit durability, and recovery of UCON state and outbox work.

A single PostgreSQL container, a second connection, a row-level writer epoch, or a mocked promotion is not a multi-node HA experiment. Results must come from at least three independent PostgreSQL processes with independent data directories, streaming replication, a real failover controller, and controlled network/process faults.

This document defines the protocol and acceptance criteria. It does not claim that the topology has been provisioned or that any experiment has passed.

## Research questions

- RQ1 — Does the failover controller prevent two writable primaries during process failure and network partition?
- RQ2 — Which client-acknowledged commits survive promotion under asynchronous and synchronous replication?
- RQ3 — Does the new primary reject operations carrying the old writer epoch after promotion?
- RQ4 — Are policy changes, revocations, resource mutations, invocation receipts, and outbox records recovered consistently?
- RQ5 — Can an uncertain client outcome be reconciled using the original invocation ID without duplicating the protected effect?
- RQ6 — What are the observed RPO, RTO, stale-write acceptance count, and outbox recovery characteristics under each fault?

## Required topology

- PostgreSQL primary P1 and two physical streaming standbys P2/P3, each with an independent persistent data volume.
- A quorum-backed DCS with three members (for example, three-node etcd).
- A real PostgreSQL HA controller (for example, Patroni) responsible for leader election, demotion, and promotion.
- A client endpoint that follows the controller's current leader (for example, HAProxy plus health checks); direct node endpoints remain available to the adversarial test harness.
- A separate test driver recording invocation/response timestamps and acknowledged transaction identifiers.
- A controllable fault injector able to stop processes and partition selected network paths without deleting database volumes.

All components must have pinned image versions and explicit health checks. The DCS must have a real quorum; a single etcd node is not acceptable.

## Replication modes

Run at least two independent configurations, resetting the topology between configurations:

1. **Asynchronous mode:** synchronous_standby_names disabled. Record synchronous_commit, remote-write behavior, and the promoted standby's replay LSN.
2. **Synchronous mode:** configure a named synchronous standby policy (for example, ANY 1 (P2,P3)) and the required synchronous_commit level. Verify at runtime which standby is synchronous and which WAL position has been acknowledged.

Do not infer zero RPO from a configuration string. Prove whether each acknowledged transaction's WAL record is present on the promoted node. A synchronous configuration that blocks commits when no qualifying standby is available is an availability trade-off, not automatically a test failure.

## Workload and state under test

For each trial, create a fresh resource and principal, grant a UCON action, and capture resource version, policy version, authorization epoch, and writer epoch. Drive:
- ordinary resource mutations;
- policy-version updates;
- principal revocations;
- outbox-producing accepted mutations;
- receiver inbox processing and local effect application.

The test driver must persist a trial ledger outside the PostgreSQL cluster containing invocation ID, command digest, request-send time, client-observed acknowledgement/rejection/timeout, primary identity, and known WAL/LSN markers. This ledger is necessary to detect a commit acknowledged to a client but absent after promotion.

## Fault campaigns

Repeat each campaign at least 30 times per replication mode, with a fixed random seed recorded for randomized timing. Preserve raw trial records, including failed and inconclusive trials.

| Campaign | Fault injection | Required observations |
|---|---|---|
| F1 — primary crash | Stop P1 abruptly after a controlled write burst | Election, promotion, acknowledged transaction survival, RTO |
| F2 — primary isolation | Partition P1 from DCS and application network while leaving P1 alive | Whether P1 is demoted/fenced; whether any stale write is accepted |
| F3 — standby loss | Stop one standby before writes and failover | Synchronous commit blocking/degradation; promotion eligibility |
| F4 — DCS member loss | Stop one DCS member, then two (quorum-loss negative control) | Leadership changes only with quorum; behavior without quorum |
| F5 — revoke/mutate race | Revoke a principal while a protected mutation is in flight during failover | No mutation accepted after a completed revocation under the declared serialization contract |
| F6 — policy/mutate race | Change policy while a protected mutation is in flight during failover | Stale policy snapshot rejected |
| F7 — uncertain response | Drop client response after server commit, then promote | Invocation reconciliation and no duplicate mutation using the same invocation ID |
| F8 — outbox recovery | Crash publisher/primary around claim, send, receiver commit, and acknowledgement | Event replay, lease fencing, receiver deduplication, no duplicate receiver-local effect |
| F9 — old-primary rejoin | Restore isolated former primary after promotion | Former primary remains non-writable or rejoins as a standby; no divergent writes accepted |

F2 is mandatory. If the old primary can still commit writes to divergent storage, record a split-brain counterexample and mark the safety objective failed.

## Measurements and operational definitions

- **RPO (transactions):** count of client-acknowledged committed invocations absent from the promoted primary. Report denominator and lost invocation IDs.
- **RPO (time):** difference between latest acknowledged commit timestamp and latest recoverable commit timestamp; report clock uncertainty.
- **RTO:** elapsed time from fault injection to first successful authorized read and mutation through the client endpoint. Report read and write RTO separately.
- **Stale-write acceptance:** operations accepted by a former or promoted primary using a stale writer epoch or stale authorization snapshot. Target: zero.
- **Split-brain duration:** interval during which more than one node can commit writes. If not directly observable, report unknown, not zero.
- **Safety violation:** mutation accepted after a completed revocation/policy fence contrary to the declared serialization order, or stale-writer mutation accepted after the old writer is declared fenced.
- **Outbox recovery:** producer events recovered, redelivered, acknowledged, dead-lettered, and absent after promotion.
- **Duplicate delivery:** transport deliveries per event ID, separate from duplicate receiver-local effects.
- **Receiver deduplication:** repeated event IDs deduplicated by inbox digest; altered payload under an existing event ID must be rejected.
- **Availability:** failed/blocked client operations during failover, including synchronous commit blocking.

Report median, p95, maximum, and empirical RTO distribution. For proportions/counts, report numerator, denominator, and exact confidence intervals. Requests within one failover episode are not independent failover trials.

## Safety and liveness criteria

### Safety (must hold in every trial)

1. No two PostgreSQL nodes accept protected writes concurrently.
2. Once externally fenced, direct access to a former primary cannot commit protected writes.
3. The promoted primary has a strictly greater writer epoch before protected application traffic is admitted.
4. Every protected writer validates writer epoch and UCON policy/revocation/resource state in the same transactional authority.
5. A completed revocation or policy update fences later protected mutations according to database serialization order.
6. An invocation ID cannot produce two different committed effects.
7. The outbox event and accepted producer mutation are atomic on the producer database.
8. Receiver-local effect and inbox deduplication are atomic in the receiver database.

### Liveness / availability (measure, do not assume)

- The controller elects and exposes a healthy primary when DCS quorum and an eligible replica exist.
- Authorized writes eventually resume after a recoverable failure.
- Under synchronous mode, write blocking when no synchronous standby is available is expected if required by the durability contract.
- With no DCS quorum, the system must fail closed rather than permit unsafe promotion.

## Analysis plan

1. Validate trial integrity and unique invocation IDs.
2. Reconstruct the acknowledged-commit set from the external trial ledger.
3. Compare it with invocation records, resource state, event log, and outbox rows on the promoted primary.
4. Verify writer epochs and controller leadership transitions from timestamped logs.
5. Run the G7 finite-history linearizability checker on complete histories; classify incomplete histories as UNKNOWN rather than dropping them.
6. Classify outcomes as PROVED, MODEL_CHECKED, TESTED, EMPIRICAL, CONDITIONAL, OPEN, or REJECTED.
7. Publish raw data, scripts, topology manifest, controller configuration, commands, logs, and analysis code with checksums.

## Acceptance and falsification

G7.8 cannot be marked successful merely because automatic promotion works.

- **Safety pass:** zero split-brain/stale-write/UCON ordering violations across all trials, plus evidence that old-primary fencing is enforced by the actual controller/network/compute layer.
- **Durability pass:** RPO satisfies the explicitly selected contract. If zero loss is promised for acknowledged writes, any lost acknowledged transaction falsifies the claim.
- **Recovery pass:** invocation reconciliation and outbox/inbox recovery meet the stated semantics; UNKNOWN outcomes remain explicit where RPO cannot resolve them.
- **Performance characterization:** RTO and availability are reported with distributions; no universal SLO is inferred without a target.
- **Reproducibility pass:** another operator can recreate the exact topology and reproduce each fault campaign from committed artifacts.

A single observed safety violation is a counterexample and blocks the corresponding guarantee. Missing telemetry, ambiguous acknowledgement status, or an unverified fault is INCONCLUSIVE, not PASS.
