# G6.1 — Threat model, trusted computing base, and enforcement boundary

**Status:** specification baseline; not implementation-validated  
**Stage:** G6.1  
**Date:** 18 November 2026  
**Depends on:** G4 operational semantics, G5 workflow-level statistical assurance

## 1. Purpose and normative boundary

G6 establishes whether the G4 enforcement claims can be represented by an executable transition system and checked under explicit concurrency and failure assumptions.

The governing separation is:

1. **UCON is authoritative.** Only the formal policy evaluator and execution gate may authorize a protected operation.
2. **JEPA is advisory.** It may recommend admission, restriction, escalation, or abstention. It cannot grant a permission, mint an authorization certificate, suppress an obligation, or bypass a gate.
3. **The external effect is the security boundary.** A governance database commit, audit event, or agent-visible success message is not necessarily the moment a remote side effect becomes effective.
4. **A guarantee is scoped to a declared tool protocol.** If a tool exposes no reliable acceptance receipt, cancellation semantics, idempotency key, or effect evidence, the corresponding property is not silently assumed.

This document is a threat-model and architecture contract. It is not evidence that a deployed system already satisfies the assumptions.

## 2. System model and principals

The abstract system contains the following principals and components.

| Symbol | Principal/component | Security responsibility |
|---|---|---|
| A | Autonomous agent / planner | Proposes workflow plans and action invocations; untrusted for authorization |
| J | JEPA predictor and risk head | Computes predictive evidence; advisory and potentially faulty |
| P | Policy administration plane | Publishes versioned UCON policies and policy metadata |
| E | UCON policy evaluator | Evaluates current authorization, conditions, and obligations |
| G | Execution gateway / reference monitor | Complete mediation, certificate binding, freshness checks, effect-boundary coordination |
| T | Tool adapter / connector | Translates a typed invocation to a concrete external API operation |
| S | External service | Performs or accepts the requested side effect |
| V | Effect verifier / reconciler | Collects receipts, reads back state, and classifies observed outcomes |
| L | Append-only audit and intent log | Records durable intent, decisions, receipts, and recovery state |
| H | Human approver / operator | Performs explicitly delegated approval or incident response |

The logical agent identity and effective execution principal are distinct. The effective principal is the identity actually recognized by the external service (for example, a workload identity, service principal, delegated user, or scoped credential). Authorization must bind to the effective principal and the delegation chain, not merely to the LLM's conversational identity.

## 3. Protected assets

The model protects:

- confidentiality, integrity, and availability of enterprise data and services;
- identity, credentials, delegated authority, sessions, and capabilities;
- policy versions, obligations, conditions, and approval decisions;
- workflow state, provenance, lineage, and security labels;
- external side effects such as cloud resource creation/deletion, financial transfers, data export, permission changes, and SaaS mutations;
- integrity and completeness of intent, decision, effect, and recovery records;
- model, score, calibration certificate, policy, tool-schema, and evaluator version bindings.

The predictive model itself is not a root of trust. Compromise of J may cause excess denials, unnecessary approvals, or missed warnings, but must not create authority to execute an operation.

## 4. Adversary and fault model

### 4.1 Adversarial behaviour in scope

The agent, its generated plan, tool arguments, and retrieved content are treated as untrusted inputs. An adversary may:

- prompt-inject or manipulate an agent into proposing unauthorized operations;
- exploit confused-deputy conditions or identity/delegation mismatches;
- replay, duplicate, reorder, or mutate invocations;
- race an invocation against capability revocation, session expiry, policy updates, or resource-state changes;
- exploit stale caches, asynchronous execution, retries, duplicate delivery, and partial failures;
- cause the planner to alter a plan after predictive assessment;
- exploit a tool adapter that omits a protected operation from mediation;
- provide malformed, ambiguous, oversized, or adversarial action arguments;
- induce a JEPA false negative, false positive, high uncertainty, or out-of-distribution score;
- cause missing, delayed, duplicated, or contradictory effect evidence.

### 4.2 Faults in scope

The model considers crash-stop failures of the gateway, adapter, agent, verifier, or log writer; network partitions and timeouts; delayed or duplicated messages; stale replicas; external-service asynchronous completion; and ambiguous outcomes where a request may have been accepted even though the caller timed out.

The model does **not** assume Byzantine correctness of the external service, the operating system, cryptographic primitives, or the trusted policy evaluator. Where a component is outside the TCB, its output is treated as evidence requiring validation rather than truth by definition.

### 4.3 Explicitly out of scope for the initial model

The first TLA+ model will not prove resistance to arbitrary kernel compromise, malicious cloud-provider control planes, cryptographic breaks, arbitrary Byzantine replicas, covert channels, side-channel leakage, or correctness of business policy itself. These require separate threat models and evidence.

## 5. Trusted computing base (TCB)

The minimum TCB for the authorization-soundness claim is:

1. **Identity and credential binding:** authenticates the effective principal and delegation context.
2. **Policy evaluator:** implements the declared UCON semantics correctly.
3. **Authoritative policy/state source:** provides the versions and values used at the decision boundary.
4. **Execution gateway/reference monitor:** mediates every protected effect and validates invocation-bound authorization.
5. **Tool adapter for each protected operation class:** preserves the exact action, target, arguments, principal, and idempotency/correlation identifiers.
6. **Effect-boundary protocol:** provides a defensible linearization point or a conservative equivalent.
7. **Certificate and message integrity:** prevents forgery, rebinding, and replay.
8. **Durable intent/audit mechanism:** preserves enough information for recovery and reconciliation, subject to stated durability guarantees.

The JEPA encoder, predictor, risk head, threshold selector, and dashboard are **not** in the authorization TCB. The verifier is in the TCB only for claims that depend on the truth/completeness of observed mutation evidence. A human approval service becomes part of the TCB for any policy path that delegates authority to that approval.

A deployment may have a larger TCB. It must not have a smaller one for the stated theorem unless an equivalent mechanism is justified.

## 6. Trust boundaries and mandatory mediation

The protected path is:

Agent → typed request → identity/delegation binding → UCON evaluator → optional JEPA risk restriction → execution gateway → tool adapter → external service

The audit/intent log and verifier observe and reconcile this path. The agent must not possess an alternate credential or network route that permits protected effects without the gateway. The gateway must mediate at the last controllable point before the external service accepts the effect.

A proxy in front of a tool is not sufficient if the same credentials remain usable by the agent through a direct route. Complete mediation requires both:
- **routing control:** all relevant network/API paths pass through the gateway or an equivalent reference monitor; and
- **credential control:** the agent cannot independently exercise the effective external authority.

For each protected tool, maintain an operation inventory mapping (service, API operation, effect class) to its adapter, gate, effect boundary, evidence source, idempotency semantics, and recovery strategy. Unknown operations fail closed or are excluded from the protected guarantee and explicitly documented.

## 7. Effect semantics and linearization point

For invocation i, distinguish these events:

- Request(i): an agent submits a typed request;
- Authorize(i): the evaluator issues a decision bound to the exact action and versions;
- Prepare(i): optional reservation or preflight that has no protected irreversible effect;
- Dispatch(i): the adapter sends the operation;
- Accept(i): the external service accepts the operation or crosses its irreversible-effect boundary;
- Observe(i): the system obtains an authoritative receipt or read-after-write observation;
- Verify(i): the verifier checks the effect against the expected mutation relation;
- Commit(i): governance state records the verified outcome;
- Compensate(i) / Contain(i): recovery action after an inconsistent or uncertain outcome.

The security-relevant **effect linearization point** is Accept(i), not Commit(i). For synchronous APIs this may be the atomic service-side mutation. For asynchronous APIs it may be job creation/acceptance, even if the job's final effect occurs later. If acceptance merely schedules a later operation whose execution can be revoked, the adapter must model both acceptance and final effect as separate protected events.

The G6 model will represent the external service boundary explicitly. It will not collapse Dispatch, Accept, Observe, and Commit into one atomic action.

### 7.1 Revocation semantics

A revocation request is not immediately effective. Define EffectiveRevoke(c) as the instant at which the revocation is visible to every relevant effect gate, or at which a linearizable coordination protocol guarantees that no later gate can accept an operation using capability c.

The target property is:

EffectiveRevoke(c) < Accept(i) ⇒ Accept(i) is not permitted using c.

If Accept(i) linearizes before EffectiveRevoke(c), revocation does not retroactively undo that effect. In-flight asynchronous jobs require a separate cancellation/containment contract; no instantaneous cancellation is presumed.

### 7.2 Policy-update semantics

A policy update has a request/prepare phase and an effective publication point EffectivePolicy(v+1). The gate must serialize this point with effect acceptance or reject/revalidate an invocation whose policy version is stale at Accept(i).

A policy update cannot undo an effect already accepted under the prior policy. The exact semantics of pending asynchronous jobs must be specified per tool class.

### 7.3 State-version semantics

A state version check alone does not imply serializability. If authorization depends on mutable resource state, the effect protocol must either atomically compare-and-apply against the relevant version, lock/reserve the relevant resource, use a serializable transaction, or provide a proved equivalent. Otherwise, a time-of-check/time-of-use race remains possible.

## 8. JEPA-specific isolation contract

JEPA may return one of: ALLOW_RECOMMENDATION, RESTRICT, ESCALATE, or ABSTAIN. These are advisory classifications, not authorization decisions.

The following noninterference condition is mandatory:

> Holding the UCON state, policy, identity, and request fixed, changing or removing JEPA output must never turn a UCON-denied operation into an executable operation.

A predictor failure, timeout, corrupted model, certificate mismatch, or out-of-distribution signal may cause a conservative fallback (abstain, restrict, or escalate). It must never disable the UCON gate. The policy may require a predictive certificate as an additional condition for selected high-risk actions, but a passing JEPA score is never sufficient authorization.

The candidate plan assessed by JEPA must be bound to the action sequence and relevant context. Any plan mutation invalidates the predictive assessment unless a separately specified suffix/policy-induced assessment applies. This does not replace per-action UCON checks.

## 9. Security properties to model

G6.2/G6.3 will encode at least the following properties.

| ID | Property | Informal statement |
|---|---|---|
| SEC-1 | Complete mediation | Every protected Accept has a preceding successful gate check |
| SEC-2 | Authorization soundness | Every accepted effect is admitted under the effective policy/state |
| SEC-3 | Revocation safety | No capability use is accepted after effective revocation |
| SEC-4 | Policy freshness | No effect is accepted under a stale policy version |
| SEC-5 | Invocation binding | A certificate cannot authorize a different invocation/action/principal |
| SEC-6 | At-most-once acceptance | Duplicate/replayed invocation identifiers do not cause duplicate protected acceptance, where the tool supports idempotency |
| SEC-7 | Commit discipline | No successful governance commit occurs without verified effect evidence |
| SEC-8 | JEPA non-authority | JEPA output cannot create authority or bypass formal denial |
| SEC-9 | Recovery honesty | An ambiguous external outcome is represented as unknown/reconciliation-required, not falsely committed or blindly retried |
| SEC-10 | Mutation invariant | The declared resource invariant is preserved under the chosen concurrency protocol |

Liveness properties (eventual completion, eventual reconciliation, bounded latency) are separate from safety and require fairness, availability, and service-response assumptions. G6 will not infer liveness from safety invariants.

## 10. Tool classes and limits of guarantees

Each tool adapter must be classified before a property is claimed.

| Class | External API behaviour | Required model treatment |
|---|---|---|
| T1: synchronous atomic | One request has a well-defined atomic effect/acceptance | Single Accept linearization point |
| T2: asynchronous job | Request acceptance creates a job; job later changes state | Model AcceptJob and CompleteEffect separately; specify cancellation |
| T3: idempotent retry | Stable idempotency key deduplicates retries | Model key binding and duplicate response semantics |
| T4: non-idempotent/ambiguous | Timeout may follow successful acceptance; no reliable deduplication | Enter UNKNOWN; reconcile before retry |
| T5: transactional conditional | Service supports compare-and-swap/ETag/transaction preconditions | Model version predicate atomically with effect |
| T6: weakly observable | No reliable receipt/read-after-write evidence | Do not claim verified mutation consistency; require containment/manual reconciliation |

No global theorem may silently assume that every enterprise tool behaves like T1. Guarantees are per operation class and per adapter contract.

## 11. Initial assumptions to be challenged by model checking

The initial finite-state model may assume:
- a finite set of agents, capabilities, policies, resources, and invocations;
- atomic transitions for explicitly declared linearization events;
- a correct abstract policy evaluator;
- an honest reference model of service acceptance;
- a durable log abstraction when testing write-ahead intent;
- bounded message delay represented by nondeterministic interleavings, not real-time bounds.

These assumptions are abstractions, not facts about production. The model must include adversarial interleavings and failure points around every non-atomic boundary. Any property that holds only because an operation was made atomic in the model must be labelled as conditional on implementing that atomicity.

## 12. Required implementation evidence

| Assumption / claim | Required evidence |
|---|---|
| Complete mediation | API/operation inventory, credential isolation, network-path tests, direct-bypass negative tests |
| Identity binding | Effective-principal and delegation-chain tests; confused-deputy tests |
| Certificate integrity | Cryptographic binding, invocation/action/version binding, replay/substitution tests |
| Policy correctness | Reference semantics and differential tests against the production evaluator |
| Linearizable effect gate | Tool-specific protocol, race tests, model-checking correspondence |
| Revocation effectiveness | Defined propagation/linearization protocol and revoke-vs-accept race tests |
| Policy update safety | Update-vs-pending-invocation race tests |
| State consistency | Transaction/isolation/CAS evidence; concurrent invariant tests |
| Mutation verification | Receipt/read-after-write specification, verifier tests, evidence completeness analysis |
| Recovery | Crash injection at dispatch/accept/observe/verify/commit boundaries; reconciliation tests |
| JEPA non-authority | Architecture graph, permission tests, predictor failure/false-negative fault injection |

## 13. Explicit non-claims

G6.1 does not claim:
- that revocation can cancel an already accepted or running external operation;
- that all tools expose a linearizable effect boundary;
- that an audit log proves an external effect occurred;
- that a remote success response proves the intended mutation without a trusted service contract;
- that all state changes are serializable;
- that a JEPA score is a probability or an authorization result;
- that a sandbox/model-checking result transfers automatically to production;
- that TLA+ model checking proves the implementation correct without a refinement/correspondence argument.

## 14. G6.1 exit criteria

G6.1 is complete as a specification stage when:
1. the threat model and TCB are committed;
2. effect, revocation, and policy-update linearization semantics are explicit;
3. JEPA's non-authority boundary is stated as a safety property;
4. tool classes and non-claims are explicit;
5. the G6.2 transition system can be derived without inventing hidden atomicity assumptions.

**Exit status:** specification drafted. Implementation evidence and formal model checking remain open.
