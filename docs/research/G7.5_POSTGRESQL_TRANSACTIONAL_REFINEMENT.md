# G7.5 — PostgreSQL transactional refinement

## Scope

G7.5 adds a PostgreSQL 16 implementation of the same single-authority reference transition used by G7.3/G7.4. It is an executable refinement candidate, not a theorem about arbitrary PostgreSQL deployments or external effects.

Implementation: `src/ucon_jepa/postgres_service.py`

Integration tests: `tests/G7/test_postgres_service.py`

CI: the G7 workflow runs a dedicated PostgreSQL 16 service job and installs psycopg 3.

## Serialization protocol

All protected state is in one PostgreSQL database:

- `ucon_control_state`: singleton policy version and authorization epoch;
- `ucon_resources`: resource version and payload;
- `ucon_grants` and `ucon_revoked`: authorization state;
- `ucon_invocations`: durable invocation-key/digest/result mapping;
- `ucon_events`: append-only transaction-coupled event records.

Every protected writer first executes:

```sql
SELECT policy_version, authorization_epoch
FROM ucon_control_state
WHERE singleton = 1
FOR UPDATE;
```

It then reads/changes the resource and writes the invocation and event records in the same transaction. Grant, revoke, policy update and mutation all acquire this same row lock first. The lock is held until transaction commit or rollback. Resource mutation additionally uses a row lock and a version-conditional update.

The intended ordering argument is:

1. PostgreSQL grants at most one transaction the exclusive row lock on the singleton control row at a time.
2. Each protected writer holds that lock through its authorization decision and commit.
3. Therefore protected writers have a total order consistent with lock acquisition/commit serialization for this control row.
4. A mutation checks the policy version and authorization epoch while holding the lock. A revocation or policy update that commits first is visible to a later mutation; a mutation that commits first is ordered before that update.
5. The resource update, event and idempotency record commit or roll back together.

This is a conditional database-level argument. It assumes all relevant writes use this service/protocol and the same primary database. Direct SQL writers, split databases, stale replicas, cache-authorized effects, bypass paths or external side effects invalidate the refinement boundary.

## Isolation and operational assumptions

The implementation uses PostgreSQL's default `READ COMMITTED` isolation plus explicit `SELECT ... FOR UPDATE` on the singleton control row. It does not rely on a claim that READ COMMITTED alone provides serializable transactions. The singleton lock is the explicit serialization mechanism for protected writers.

Assumptions requiring deployment verification:

- one authoritative PostgreSQL primary for this state;
- PostgreSQL row-lock and transaction semantics behave as specified;
- all protected policy, grant, revocation and resource writes acquire the control lock first;
- application role cannot bypass the service using direct table writes;
- connection loss, failover and commit acknowledgement semantics are handled by the deployment;
- database durability configuration and backup/restore preserve committed invocation records and effects;
- trusted identity and delegation bindings are supplied upstream;
- the protected effect is the database row update itself, not an external API call.

The code's `initialize()` method is an idempotent bootstrap for tests and prototypes. Production deployment must use reviewed, versioned schema migrations, least-privilege roles, TLS, secrets management, backups, monitoring and a tested failover policy.

## Idempotency and recovery

The invocation key and canonical command digest are stored in the same transaction as the mutation. Repeating the identical invocation returns the original result. Reusing the key with a different command is rejected. A failure before commit rolls back all three records/effects. If the commit succeeds but the response is lost, retry returns the stored receipt.

The post-commit fault hook is deliberately invoked only after an explicit `conn.commit()`. This simulates response loss after commit acknowledgement at the adapter boundary; it is not a process-kill or power-loss test.

## Integration tests

The PostgreSQL suite covers:

- successful mutation and durable idempotent replay;
- invocation-key collision with a different command;
- revocation denial using a fresh authorization snapshot;
- policy-update fencing of a stale snapshot;
- 12 concurrent mutations against one resource version, expecting exactly one acceptance;
- rollback after injected pre-commit failure;
- response loss after commit and replay of the original receipt.

The CI job runs these against PostgreSQL 16, not SQLite. The broader G7 unit suite remains a separate job.
