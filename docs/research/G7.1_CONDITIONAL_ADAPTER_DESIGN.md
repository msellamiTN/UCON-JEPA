# G7.1 — Conditional API adapter design

## Objective

Refine the G6 abstract acceptance boundary into a concrete synchronous HTTP adapter whose mutation is conditional on a version token supplied by the authoritative resource service. The first reference target is an HTTP resource supporting strong ETags and atomic `If-Match` evaluation (HTTP conditional request semantics).

This stage is deliberately a **reference adapter contract**, not a production gateway and not evidence that an arbitrary REST API implements the required semantics.

## Security and consistency model

An invocation is bound to the tuple

`(invocation_id, effective_principal, action, target, capability, policy_version, resource_etag, authorization_epoch)`.

The adapter accepts an immutable, already validated gate decision. It does not ask JEPA to authorize. A positive JEPA recommendation is never an authorization input.

Before mutation, the adapter requires:
- a non-empty invocation ID and effective principal;
- an allow decision from the reference monitor;
- a non-empty strong ETag (weak ETags are rejected);
- an authorization epoch and policy version;
- a fixed target and action;
- a request body digest supplied by the caller or computed locally;
- an idempotency key equal to the invocation ID.

The adapter sends a conditional mutation with `If-Match: <strong-etag>` and `Idempotency-Key: <invocation-id>`. A 412 response is a conflict and is never retried automatically. A transport timeout is UNKNOWN: the remote effect may have happened, so the adapter must not blindly replay a non-idempotent request. A 2xx response is an acceptance receipt only; it is not proof that the desired postcondition holds. Independent observation and verification remain mandatory before governance commit.

## Crucial linearizability condition

A resource ETag alone protects only the resource version. It does **not** make a separate revocation database or policy store atomic with the resource mutation.

For the G6 acceptance theorem to refine to a real deployment, the service must atomically validate both:
1. the resource version; and
2. the current authorization/policy epoch (or an equivalent fencing token),

at the same server-side linearization point as the mutation. This can be implemented by a service-side transaction, a conditional command endpoint, or a co-located authorization epoch in the same versioned record. A client-side check followed by an ordinary REST write has a TOCTOU race and is explicitly insufficient.

If the remote API cannot provide this joint atomic condition, the adapter must label the guarantee as **resource-CAS only**, and revocation/policy freshness remain OPEN at the external effect boundary.

## Response semantics

| Result | Adapter classification | Automatic retry |
|---|---|---|
| 200/201/204 | ACCEPTED; receipt captured | No |
| 412 | CONFLICT; precondition failed | No; reauthorize and reread |
| 401/403 | REJECTED by service | No |
| 429/5xx | UNKNOWN unless API contract proves no mutation | No by default |
| timeout / connection reset after send | UNKNOWN | Never blindly replay |
| malformed or uncorrelated receipt | UNKNOWN | No |

A service-specific contract may refine 429/5xx only with documented, tested guarantees that no mutation was applied.

## Scope and non-goals

In scope: synchronous conditional mutation, strict ETag handling, idempotency key propagation, explicit conflict/unknown outcomes, deterministic fake-transport tests.

Out of scope: cryptographic token issuance, real identity-provider integration, durable write-ahead log, asynchronous jobs, distributed revocation transactions, production deployment, and claims about arbitrary APIs.

## G7 proof obligations

- **P7.1 (Binding):** the adapter's target, method, body digest, invocation and principal are immutable after gate approval.
- **P7.2 (Conditional mutation):** a successful mutation carries the expected strong ETag and authorization epoch.
- **P7.3 (No stale resource write):** under the server's atomic strong-ETag contract, a resource version mismatch cannot be accepted.
- **P7.4 (No unsafe retry):** conflict and UNKNOWN outcomes are never automatically replayed.
- **P7.5 (Joint enforcement refinement):** if policy/revocation epoch is atomically checked by the target service, acceptance implies the epoch matched at the effect linearization point. This is conditional on the target service contract; it is not proved by client code.
- **P7.6 (Verification separation):** HTTP success does not set observed, verified, or committed.

## Evidence labels

Code-level behavior can be TESTED with the fake transport. ETag safety is CONDITIONAL on correct server implementation of HTTP conditional semantics. Joint revocation/policy linearizability is OPEN until a concrete target API demonstrates an atomic combined precondition. Production security remains OPEN.
