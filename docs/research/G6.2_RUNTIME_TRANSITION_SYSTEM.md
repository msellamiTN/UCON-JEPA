# G6.2 — Explicit runtime transition system

**Status:** formal transition-system specification; not yet model-checked  
**Stage:** G6.2  
**Depends on:** G6.1 threat model and enforcement boundary

## 1. Objective

This stage converts the G6.1 event semantics into a labelled transition system (LTS). The LTS separates request admission, authorization, preparation, dispatch, external acceptance, observation, verification, governance commit, and recovery. It exposes the concurrency points at which revocation, policy publication, state mutation, retries, and crashes may interleave.

The model is protocol-neutral. Tool-specific atomicity is an explicit adapter contract, not a global assumption.

## 2. State space

Let I be a finite set of invocation identifiers, C a finite set of capabilities, R a finite set of protected resources, P a finite set of policy versions, and A a finite set of typed actions.

For each invocation i, state contains:
\[
action[i], principal[i], capability[i], planHash[i], status[i],
certPolicy[i], certState[i], certAction[i],
gatePassed[i], dispatched[i], accepted[i], observed[i],
verified[i], committed[i], outcome[i], idempotencyKey[i].
\]

Global state contains:
\[
\Sigma=(policyVersion,stateVersion,revoked,policyRules,
resourceState,usedInvocations,intentLog,effectLog,crashState).
\]

The abstract policy predicate is:
\[
Allowed(\Sigma,i)\equiv PolicyAllows(policyRules,policyVersion,
action[i],principal[i],capability[i],resourceState,stateVersion).
\]
It is a deterministic reference predicate in the initial finite model. Its implementation correctness is an external assumption, not a theorem obtained from model checking.

## 3. Lifecycle

The nominal lifecycle is:
\[
REQUESTED\to AUTHORIZED\to PREPARED\to DISPATCHED
\to ACCEPTED\to OBSERVED\to VERIFIED\to COMMITTED.
\]
PREPARED is optional. Other transitions include REQUESTED to DENIED; pre-dispatch abort; DISPATCHED to UNKNOWN after an ambiguous response; accepted/observed states to RECONCILIATION_REQUIRED; and verified outcomes to compensation or containment when required.

UNKNOWN does not mean the remote service did not accept the request.

## 4. Labelled transition relation

Write \(\Sigma\xrightarrow{\ell}\Sigma'\) when event \(\ell\) changes the global state.

### 4.1 Request

Request records a fresh invocation's immutable action, effective principal, capability, plan hash, and idempotency key. Duplicate identifiers are rejected or resolved to the existing invocation according to the adapter contract.

### 4.2 Formal authorization

Authorize is enabled only for REQUESTED invocations. The evaluator reads authoritative policy and state. If the formal predicate is false, status becomes DENIED. Otherwise, it emits an immutable certificate bound to:
\[
(i,action[i],principal[i],capability[i],policyVersion,stateVersion).
\]
The certificate cannot be rebound to another invocation, action, principal, or plan.

### 4.3 Predictive restriction

JEPA may return ALLOW_RECOMMENDATION, RESTRICT, ESCALATE, or ABSTAIN. Its output may add restrictions but cannot create a certificate, change the formal policy predicate, or set gatePassed. A positive JEPA output is never sufficient authorization.

### 4.4 Prepare

Prepare may reserve resources or obtain a preflight token. The adapter must state whether preparation is side-effect-free, reversible, or itself a protected effect. If protected, preparation must pass its own gate.

### 4.5 Gate and dispatch

GateCheck validates certificate/action/principal/capability binding, current policy compatibility, current state compatibility, non-revocation, invocation freshness, and any policy-mandated predictive restrictions.

A successful check is insufficient if relevant state may change before remote acceptance. The adapter must serialize GateCheck with Accept, use atomic compare-and-apply, hold a valid reservation/lock, or prove an equivalent protocol.

Dispatch sends the immutable request and correlation/idempotency key to the external service. Dispatch is not acceptance.

### 4.6 External acceptance

Accept is the effect-boundary event. It is enabled only when the adapter contract establishes that the GateCheck remains valid at this point. The transition records acceptance and consumes the invocation/idempotency key.

For synchronous atomic APIs, Accept may coincide with the service-side mutation. For asynchronous APIs, AcceptJob creates a job and CompleteEffect is a separate event. Revocation after AcceptJob is not presumed to cancel the job.

### 4.7 Observation and verification

Observe records a service receipt, job status, or authoritative read-after-write evidence. Verify checks provenance, correlation to the invocation, completeness, and the expected mutation relation. Missing or ambiguous evidence leads to UNKNOWN or RECONCILIATION_REQUIRED, never COMMITTED.

### 4.8 Commit

Commit is enabled only after successful verification and satisfaction of the durable intent/effect-log protocol. It records the verified outcome in governance state. It does not redefine the earlier external-effect boundary.

### 4.9 Revocation and policy update

RequestRevoke records an administrative request only. EffectiveRevoke changes authoritative revocation state at a linearization point serialized against Accept. Later acceptance using that capability is disabled. Earlier accepted effects are not retroactively undone.

PublishPolicy changes the authoritative policy version at a linearization point serialized against Accept. A certificate for an incompatible old policy cannot be used by a later Accept.

### 4.10 State mutation and concurrency

Mutate is enabled only under the adapter's concurrency protocol. The initial safe abstraction uses atomic compare-and-apply:
\[
expectedVersion=stateVersion[r]
\]
at the same linearization point as the resource mutation. If this predicate is not atomic with the effect, the model must permit a TOCTOU interleaving and expose the resulting counterexample.

### 4.11 Crash and recovery

Crashes may occur after intent logging, authorization, dispatch, acceptance, observation, verification, and around commit. Accepted effects remain accepted. A dispatched request with no definitive response may be ambiguous. Retries require a stable idempotency key or authoritative proof that no effect occurred. Absence of a local response is not evidence of remote non-acceptance.

## 5. Atomicity and event ordering

For a successful commit:
\[
Request\prec Authorize\prec GateCheck\prec Accept
\prec Observe\prec Verify\prec Commit.
\]
Prepare and predictive assessment are optional and occur before the final gate. The final gate is mandatory for every protected effect.

Revocation and policy publication may interleave between any non-atomic events. The acceptance transition resolves the race by a defined linearization protocol, not wall-clock timestamps.

## 6. Candidate safety invariants

**INV-1 — No unauthorized acceptance**
\[
\forall i:\ accepted[i]\Rightarrow AllowedAtAccept[i]\land CertificateBound[i].
\]

**INV-2 — Revocation**
\[
\forall i:\ accepted[i]\Rightarrow\neg revokedAtAccept[i].
\]

**INV-3 — Policy freshness**
\[
\forall i:\ accepted[i]\Rightarrow
certPolicy[i]=policyVersionAtAccept[i]
\]
under strict version equality.

**INV-4 — Invocation uniqueness**
\[
\forall i:\ acceptedCount[i]\le1.
\]

**INV-5 — Commit requires verification**
\[
\forall i:\ committed[i]\Rightarrow verified[i]\land observed[i].
\]

**INV-6 — JEPA non-authority:** changing JEPA output while formal state is fixed cannot enable an invocation denied by UCON.

**INV-7 — Unknown-outcome honesty**
\[
outcome[i]=UNKNOWN\Rightarrow\neg committed[i].
\]

**INV-8 — Resource invariant:** ResourceInvariant(resourceState) is preserved by every accepted concurrent mutation.

These are candidate properties to encode in TLA+, not claims already proved.

## 7. Liveness properties

Candidate liveness properties are conditional:
- every admitted, non-revoked invocation eventually reaches a terminal state if service, network, verifier, and scheduler remain available;
- every UNKNOWN invocation is eventually reconciled if authoritative evidence eventually becomes available;
- every durable intent is eventually committed, aborted, or explicitly marked unresolved.

They require fairness and availability assumptions. They do not follow from safety invariants and may fail under permanent partitions.

## 8. Refinement obligations

For every tool adapter, identify:
1. the concrete event corresponding to Accept;
2. whether it is atomic with the gate or uses CAS/transaction/lock semantics;
3. the effective principal and credentials used by the external service;
4. idempotency and retry behaviour;
5. receipt and read-after-write evidence;
6. asynchronous completion and cancellation semantics;
7. crash recovery and reconciliation behaviour.

A refinement map must map concrete states/events to abstract states/events and preserve the safety invariants. If the concrete API cannot implement the abstract atomic transition, weaken the model or withdraw the guarantee.

## 9. Counterexample scenarios required in G6.3/G6.4

- CE-G6-01: revoke after authorization but before Accept.
- CE-G6-02: policy publication after authorization but before Accept.
- CE-G6-03: two concurrent withdrawals read the same balance without atomic compare-and-apply.
- CE-G6-04: timeout after remote acceptance followed by a non-idempotent retry.
- CE-G6-05: crash after Accept but before Observe/Commit.
- CE-G6-06: JEPA predicts safe while UCON denies.
- CE-G6-07: plan hash changes after predictive assessment.
- CE-G6-08: direct credential path bypasses the gateway.
- CE-G6-09: asynchronous job accepted before revocation but completes afterward.
- CE-G6-10: verifier accepts an uncorrelated or stale receipt.

## 10. G6.2 exit criteria

G6.2 is complete when the LTS, lifecycle, event ordering, atomicity assumptions, safety/liveness split, and per-adapter refinement obligations are committed and used as the basis for the TLA+ model.

**Exit status:** transition-system specification drafted. TLA+ encoding and model checking remain open.
