# G7.7 — Writer fencing, failover reconciliation, and distributed assurance boundary

## Objective

G7.7 addresses a failure mode not covered by single-primary transaction tests: after a database promotion, clients may continue presenting state captured under an earlier writer generation, and a caller may not know whether a mutation committed before its connection failed.

The implementation adds a monotonic `writer_epoch` to the PostgreSQL control row. It is a fencing token supplied by the trusted deployment control plane, not a token that an untrusted client may choose.

Implementation:
- `src/ucon_jepa/postgres_service.py`: writer epoch, promotion transition, protected-write checks, audit tagging, and invocation reconciliation.
- `tests/G7/test_postgres_failover.py`: PostgreSQL integration tests for stale writer tokens and lookup behavior.
- The G7 PostgreSQL CI job executes the new failover suite against PostgreSQL 16.

## State and transition

Extend the abstract control state:

[
  C = (p,e,w)
]

where (p) is the policy version, (e) the authorization epoch, and (w) the writer epoch.

A protected writer carries an expected epoch (w_c). Under the same control-row lock used by the UCON protocol, the service checks:

[
  w_c = w_{db}.
]

If the equality fails, the operation is rejected with `StaleWriterEpoch` before changing resources, grants, revocations, policy, invocations, or outbox state.

Promotion on the currently authoritative database is represented by:

[
  operatorname{Promote}(w,w') quad 	ext{only if } w' > w.
]

The transition locks the control row and performs a compare-and-set update. Epochs cannot be repeated or moved backwards. A caller holding the old epoch is rejected after the promoted database has installed the new epoch.

The `require_writer_epoch` configuration makes missing tokens fail closed. It is disabled by default only to preserve compatibility with earlier reference tests; production deployments using this adapter must enable it and pass the current epoch to every protected writer.

## What this fencing does and does not prove

**Proved by the local protocol, conditional on PostgreSQL transaction/row-lock semantics:** once epoch (w') is committed on the authoritative database, a subsequent protected operation on that same database carrying (w < w') is rejected.

**Not proved by the epoch column alone:** an isolated former primary may still accept writes to its own divergent storage if it has not been externally fenced. A database row cannot coordinate two partitions that cannot communicate.

A safe HA deployment therefore needs an external failover controller and database/infra mechanisms that guarantee:
1. the former primary is demoted, powered off, network-isolated, or otherwise prevented from serving writes before the new primary is exposed;
2. the new primary is selected from the replication set according to an explicit RPO contract;
3. the new primary installs a strictly larger writer epoch before application traffic is admitted;
4. credentials, service discovery and connection pools route writers only to the promoted primary;
5. stale application instances cannot bypass the writer-epoch check;
6. all policy/resource/outbox state is in the same promoted transactional authority.

This is a fencing protocol layered on top of HA orchestration. It is not a substitute for consensus, quorum-based promotion, STONITH/compute fencing, or PostgreSQL replication guarantees.

## Acknowledged commit durability and uncertain outcomes

The idempotency table resolves a lost response only if the invocation record survived promotion. The adapter exposes `lookup_invocation(invocation_id)` to query the current authoritative database.

Interpretation:
- **Record found:** the authoritative database has a recorded result for that invocation; return the stored receipt/outcome.
- **Record absent with a zero-loss promotion guarantee for acknowledged commits:** retry/reconciliation may be governed by the deployment's idempotency protocol.
- **Record absent without such a guarantee:** outcome remains UNKNOWN. Absence on a potentially lagging or data-losing promoted node does not prove the old primary never committed.

PostgreSQL synchronous replication can reduce or eliminate acknowledged-commit loss only under a carefully configured and verified topology. The exact behavior depends on synchronous standby selection, `synchronous_commit`, failover-manager promotion rules, and whether the promoted standby contains the commits acknowledged to clients. A setting alone does not establish the whole failover guarantee. The deployment must test that the promoted node is one that satisfied the configured synchronous-acknowledgement contract.

For high-assurance operation, the deployment should:
- document RPO and RTO explicitly;
- select and test synchronous replication/standby policy appropriate to the required RPO;
- verify the failover controller promotes only a replica satisfying the acknowledged-WAL requirement;
- keep mutation requests in UNKNOWN state when the outcome cannot be reconciled safely;
- avoid blind retries with a new invocation ID;
- preserve the original invocation ID and command digest across retries;
- audit the writer epoch in mutation/revocation events.

## Outbox interaction

The writer epoch is included in the mutation event payload and enforcement audit event. The outbox remains in the producer database transaction.

After promotion:
- the publisher resumes only against the authoritative new primary;
- unacknowledged outbox rows may be redelivered;
- the receiver inbox deduplicates by event ID and payload digest;
- an event lost due to an RPO gap cannot be reconstructed from the outbox unless the producer transaction survived or an independent durable event source exists.

Therefore outbox delivery remains at-least-once conditional on durable producer state and eventual recovery. It does not bridge a replication data-loss window.

## G7.7 integration tests

The PostgreSQL suite checks:
- required writer epoch rejects missing tokens;
- promotion increases the epoch monotonically;
- stale epoch cannot update policy, revoke, create a resource, or mutate a protected resource;
- current epoch still permits a correctly authorized mutation;
- invocation lookup recovers the stored receipt and returns no row for a never-recorded identifier;
- epochs cannot repeat or move backwards.

These are tests of the adapter protocol on one PostgreSQL primary. They do **not** simulate an actual primary/standby partition, promote a replica, prove synchronous replication configuration, or establish split-brain exclusion. Those require a multi-node HA test environment and the real deployment failover controller.
