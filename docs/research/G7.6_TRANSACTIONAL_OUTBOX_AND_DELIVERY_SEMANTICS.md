# G7.6 — Transactional outbox, delivery semantics, and receiver idempotency

## Scope

G7.6 extends the PostgreSQL reference service with a transactional outbox and a receiver-side inbox. The objective is to make the database-to-message handoff recoverable without making an unsupported exactly-once claim.

Implementation:
- `src/ucon_jepa/postgres_service.py`: accepted resource mutation and outbox insertion share the same PostgreSQL transaction.
- `src/ucon_jepa/postgres_outbox.py`: leased publisher, lease fencing, retry scheduling, and receiver inbox.
- `tests/G7/test_postgres_outbox.py`: PostgreSQL integration tests.
- G7 workflow runs the outbox suite against PostgreSQL 16.

## Atomic producer invariant

For every accepted mutation with invocation identifier (i), the same transaction commits:
1. the resource version and payload update;
2. the invocation/idempotency record;
3. the mutation event record;
4. exactly one outbox row whose `event_id` and `invocation_id` are (i).

The outbox row is inserted only for ACCEPTED mutations. Replayed invocation IDs return the original mutation result; they do not create a second outbox row because the original invocation result is returned before the mutation path.

If the transaction aborts, neither the resource mutation nor the outbox row is visible. If commit succeeds but the client loses the response, retrying the same invocation ID recovers the original receipt and leaves the already committed outbox row intact.

## Publisher protocol

The publisher claims ready rows in a short transaction using:
- `FOR UPDATE SKIP LOCKED` to avoid two active claimers taking the same row concurrently;
- a lease expiration timestamp;
- a monotonically increasing `attempts` field as a fencing generation.

The network send happens outside the database transaction. On successful send, the publisher acknowledges only if its claimed attempt generation is still current. An expired worker cannot acknowledge a row that a newer worker has reclaimed. On send failure, the current lease is cleared and the row is rescheduled with bounded exponential delay.

A process crash after sending but before acknowledgement can cause the same event to be sent again after lease expiry. This is deliberate **at-least-once delivery**. It is not exactly-once delivery.

## Receiver protocol

The reference receiver writes an inbox row and a sample local effect in one PostgreSQL transaction. The inbox has a unique event ID and a digest of canonical event content:
- first delivery inserts the inbox record and applies the local effect;
- an identical duplicate sees the existing inbox record and does not apply the effect again;
- reuse of an event ID with different type or payload digest is rejected.

Thus the sample receiver's local database effect is applied at most once per event ID, conditional on inbox and effect sharing one transactional database and all receiver writes using this protocol. This does not protect an arbitrary external side effect (e.g. email, payment processor, another API) unless that downstream system itself offers an idempotency key or a transactional protocol.

## G7.6 assurance argument

Let (P(i)) denote a committed producer mutation for invocation (i), (O(i)) its outbox row, (I(i)) the receiver inbox record, and (E(i)) the receiver-local effect.

Under the single-database producer transaction assumptions:
- (P(i) iff O(i)) for accepted mutations in this implementation: both are committed or rolled back together.
- Producer retry does not create a second (O(i)), because invocation uniqueness and command-digest validation gate the mutation path.

Under the single-database receiver transaction assumptions:
- the unique inbox key permits at most one successful first-delivery insertion for (i);
- insertion of (I(i)) and (E(i)) occurs in one transaction;
- therefore at most one committed receiver-local effect is associated with (i).

The publisher may transmit (i) multiple times. The end-to-end composition therefore gives at-least-once transport and deduplicated receiver-local database effects, not a universal exactly-once guarantee.

## Fault and concurrency boundaries

Covered by integration tests:
- outbox row exists for an accepted mutation;
- receiver duplicate delivery does not duplicate the local effect;
- simulated publisher crash after receiver commit but before outbox acknowledgement causes redelivery;
- stale lease generation cannot acknowledge a newer claim;
- event ID reuse with altered payload is rejected;
- successful dispatch acknowledges after send;
- failed dispatch leaves the event undelivered and schedules retry.

Not established:
- process kill, kernel crash, power-loss, storage-controller or PostgreSQL failover behavior in a deployed environment;
- broker durability or ordering guarantees;
- delivery latency/liveness under permanent outage;
- distributed transactions spanning producer and receiver databases;
- exactly-once external side effects;
- correctness of arbitrary downstream APIs.

## Operational requirements

Production use requires versioned migrations, least-privilege DB roles, TLS, durable PostgreSQL configuration, monitored outbox age/backlog, alerting on repeated failures, bounded retention/archival, poison-event handling, dead-letter policy, and a documented replay procedure. A real broker can replace the callback transport, but the publisher must retain lease fencing and the receiver must retain idempotency.

The current schema bootstrap is a prototype convenience, not a production migration manager. Deployments must not assume that `CREATE TABLE IF NOT EXISTS` upgrades an already-created schema.
